# 阶段 5：交付（Deliver）

## 目标
把 PPT 交给用户时，附带"结论 + 证据 + 改动清单"，让用户一眼能确认效果。

## 必做事项

### 5.1 准备交付包
- [ ] PPT 文件（默认输出到 `~/Desktop/AI output/YYYY-MM-DD/[项目名]/`）
- [ ] 关键页截图（前后对比）
- [ ] 整册 contact sheet（用于缩略图级别检查）
- [ ] 改动清单（每条对应原问题）
- [ ] 验证结果：`unzip -t`、文本保留、资源检查、关键页预览

### 5.2 汇报格式（强制）

```
## 已完成 [项目名] PPT 美化

### 改动清单（共 X 处）
1. P2 文字溢出 → 改为两行文本（日期 + 周数）
2. P3-P4 日期轴错位 → 重排 + 改宽度
3. P5-P8 装饰线压图 → 删除底部装饰线
4. P8 图片压字 → 缩小图片 + 文字上移
5. ...

### 关键截图
[原 P2] → [改后 P2]：[关键差异描述]
[原 P5] → [改后 P5]：[关键差异描述]
...

### 验证结果
- 文件完整性：通过 / 未通过
- 可见文字保留：通过 / 未通过
- 图片比例：通过 / 未通过
- PowerPoint 兼容风险：无 / 有（说明）

### 验收建议
请重点检查以下页面：
- P2 / P3 / P4：日期轴可读性
- P5-P8：图文比例和位置

文件位置：[完整路径]
```

### 5.3 等待用户验收
不要主动说"应该没问题了"。**等用户**给反馈。

### 5.4 处理反馈
- 用户给"OK" → 进入 5.5
- 用户给修改意见 → 回到 execute 阶段，精准修改
- 用户给"差不多就行" → 完成，并在交付说明中记录未解决项

### 5.5 沉淀案例
只有用户已验收，且经验通过 [SKILL.md](../SKILL.md) 的“升级抽象门”、对后续多个任务确有价值时，
才提议写入 `cases/YYYY-MM-DD-项目名.md`。这是持久化写入，先给用户一个简短预览并取得确认；
普通交付不为留痕而强制创建案例。

```markdown
# 案例：[项目名]

## 背景
- 客户/场景：xxx
- 原始问题：xxx
- 改动页数：N 页

## 关键问题和解法
1. [P2 文字溢出] 根因：容器 0.65" 宽，一行放不下日期+周数 → 解法：换行（10pt + 8pt 两行）
2. [P3-P4 日期轴错位] 根因：按天精确算导致窄柱不可读 → 解法：按周粗粒度 + 比例分配
3. [P5-P8 装饰线压图] 根因：底部装饰线 y=6.95 与图片底 y=7.09 重叠 → 解法：删除装饰线
4. [P8 图片压字] 根因：图片过大、起始 y 偏下 → 解法：缩小到 2.65x4.95，y 调到 1.80
5. [P4 黑色月份数字] 根因：遗留"文本框 27"含多行月文本 → 解法：删除该文本框

## 学到的经验
- 装饰线最容易压图，养成"看到先怀疑"的习惯
- 精确算法和可读性冲突时，优先可读性
- 删除是比"挪位置"更可靠的修法
- 预览和 PowerPoint 实际打开可能不一致，交付前要查最终 PPTX
- 低清产品图不能硬拉成背景，要用高清无字底图 + 产品主体叠加

## 可复用代码
- `date_to_cumulative` 函数
- 两行文本模板
- Z-order 调整代码
```

### 5.6 提炼到知识库（如果适用）
如果这次暴露的是**新问题类型**，把对应的"问题 - 解法"提炼到 `knowledge/` 对应文件。

## 反面示例（禁止）

- ❌ 交付时不附截图（"你自己打开看吧"）
- ❌ 交付时只说"改完了"（不说改了啥）
- ❌ 用户没确认就标"完成"（"用户没反驳就是同意"）
- ❌ 未经确认自动新增案例或把一次性偏好升级成全局规则
- ❌ 不说明验证结果（用户只能自己找问题）
